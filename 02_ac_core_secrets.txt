_ac_core deobfuscated secrets
============================================================

SOURCE OF THE OBFUSCATED BLOBS
------------------------------------------------------------
Both `dtabroom.py` (as `_FALLBACK_*`) and `_ac_core.pyd` reference the
same base64 strings.  The Cython .pyd carries the primary XOR blobs;
`dtabroom.py` carries the fallback ones which happen to be identical
byte-for-byte, so recovering one recovers both.

XOR obfuscation, as implemented in `_xor_deobfuscate_fb`:
    data = base64.b64decode(data_b64)
    mask = base64.b64decode(mask_b64)
    return bytes(d ^ mask[i % len(mask)] for i, d in enumerate(data))

TLS CERTIFICATE PIN
------------------------------------------------------------
Cython-embedded class `PinningAdapter(requests.adapters.HTTPAdapter)`
takes `pin_sha256` in its constructor and raises `SSLError("Certificate
pin mismatch")` on peer-cert SHA-256 mismatch (`getpeercert(binary_form=True)`
followed by hashlib.sha256).

The pin BYTES themselves were NOT found by static searches of the .pyd
(no 64-char hex string, no 44-char base64 blob, no 32-byte high-entropy
region matching known patterns).  Possibilities:
  1. PinningAdapter is defined but never instantiated with a pin.
     Grep of `_ac_core.pyd` for the class name shows only one hit in the
     Cython string table, none in the code section that constructs it.
  2. The pin is computed at runtime from another blob we didn't
     identify.
A full reverse of _ac_core in IDA / Ghidra would resolve this.  From the
client side, the effect is that the request either goes through with
normal CA-based TLS verification (verify=True) or is refused if the pin
does not match; either way, no user data leaks over an unauthenticated
channel.
